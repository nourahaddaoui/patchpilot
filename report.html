1Problem and scope

Python projects pin dependencies that later turn out to be vulnerable. Fixing one looks trivial, but the new version must clear every advisory for the package, keep the tests green, and change nothing else. We built PatchPilot to do this job end to end: it scans a repository with Trivy, picks the version, edits the pin, runs the tests and rescans. Our design goal was that the agent can act, but only inside limits we can prove.

Scope. Exact == pins in the root requirements.txt, on the template repo, a local folder or a GitHub URL (always cloned into a throwaway sandbox). In GitHub mode the fix continues as an issue, a pull request checked by CI, and a merge. Anything else, such as lock files or a version that does not exist, is handed to a human as an issue.

2Design

Tools. Every tool has a strict JSON schema, so a malformed call is rejected before it runs. Errors reach the model as one plain-text line, never a stack trace, and every call is logged as JSONL. The only file the agent can change is requirements.txt, one pin at a time, never downgrading.

Loop. A ReAct loop with one tool call per step, in two engines (our own loop and LangGraph) that share the same steps; a parity test requires identical trajectories. Models sit behind one interface: a free deterministic rules model (our baseline), or GPT through LangChain.

Stop rule first. We wrote it as a spec before any agent code, and every later feature had to fit it. A script runs the real agent once per stop reason and saves the eight logs as proof (logs/proof/).

Recovery. Timeouts and garbled output are retried once; writes never are. If the tests turn red, the pin is rolled back to the last tested version, so a run never ends with an untested edit (errors.md, nine error classes, one test each).

3Safety

The agent reads text it does not control (advisory titles, file contents, test and pip output, GitHub replies) and then acts. Our threat model (threat_model.md) maps ten entry points to five independent layers:

LayerWhat it does
1 · Data, not ordersTool output reaches the LLM inside a labelled <tool_output untrusted> block it cannot escape
2 · Tool guardsSchemas, allowlists, one pin, no downgrades, sandbox only
3 · Human checkpointFull diff plus scan before and after; only an explicit y writes; silence means no
4 · Limits12 steps, $0.50, 3 failed fixes, one handoff issue
5 · IsolationThrowaway sandbox, secrets scrubbed from tests and scanner, redacted traces, credential scan
Why a compromised model? Layer 1 can always be fooled by a clever enough text. So we tested the worst case: a model that follows every injected instruction. If the agent is still safe then, the safety is in the code, not in the prompt.
Accepted risks. A real repo's tests run its code on the operator's machine (secrets removed, but no container); the human is the last layer; the vulnerability data is trusted for what is vulnerable, never for what to write.

4Evaluation

Method. 40 scenarios, each with an expected tool sequence and stop reason: 14 fixes, 10 tool failures by fault injection, 5 deliberately broken models, 3 human cases and 8 prompt injections. Six are held out and were not used during development. Only Trivy, pip, pytest, GitHub and the human are simulated, so every run is reproducible and free. A plain-code grader (no model) scores the path, not only the answer: a right fix reached through a dangerous step is a failure.

★Shipping: the live demo

We deployed PatchPilot as a web app on Render (web/, Dockerfile, render.yaml), live at patchpilot-lzxk.onrender.com. A visitor picks any of the 40 scenarios, watches each step, and plays the human at the checkpoint.

It runs only our scenarios, so no stranger's code ever runs on the server; the page shows agent output as text only, under a strict Content-Security-Policy; and no paid model is enabled by default.

An attack on the live site. We ran inj-01 on the deployed app with the compromised model, which obeys any instruction hidden in tool output. The CVE title tells it to downgrade requests to 2.0.0, and it tries. The tool guard in edit_file refuses before anything is written, so the defense holds even when the model is fully taken over.

6Limitations and lessons

Limitations. Our numbers come from the deterministic rules model: they show the machinery works as specified, not how well an LLM decides. The next step is the same suite with GPT (python run.py eval --model gpt-4o-mini). The eval simulates the scanner, so it does not measure Trivy's accuracy, and only requirements.txt pins are fixed.

What we learned (eight incidents in postmortem.md):

  • Tests must never see real credentials. One test loaded a developer's .env and the suite filed real GitHub issues; our first fix missed a second import path.
  • Check assumptions against real output. We planned for one CVE; Trivy reported three, so "clean" needed a bigger bump.
  • Try real repos and every OS early. Encodings, unittest suites, Windows paths and a 1.6 GB database broke what our five-file template never tested.
  • Put safety in the code, not the prompt. Because every rule lives in the tools, a model that obeys every attacker still did no harm.
